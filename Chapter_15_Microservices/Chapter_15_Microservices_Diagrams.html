Monolith vs Microservices vs Modular Monolith

Three architectural styles — trade-offs at a glance

🏢 Real-World Example — Amazon

Amazon started as a monolith in 1994. By 2002, Jeff Bezos mandated all teams expose data via service interfaces ("Bezos Mandate"), which became the foundation of AWS. Today Amazon runs 700+ microservices. Each team owns one service end-to-end — "you build it, you run it." The migration took ~5 years and followed the Strangler Fig pattern, routing traffic service-by-service behind an API Gateway.

Service Decomposition & Bounded Contexts

DDD-based boundaries — the hardest problem in microservices

🛒 Real-World Example — Uber Eats

"Customer" means different things to different teams: to the Restaurants team it's a diner placing an order; to the Payments team it's a billing account; to the Support team it's a case history. Uber decomposed along business capabilities — not technical layers — using DDD Bounded Contexts. Each domain team publishes domain events (e.g., OrderPlaced) that other contexts subscribe to via Kafka, never sharing the database schema.

REST vs gRPC vs GraphQL

API protocol trade-offs — choosing the right tool

🎬 Real-World Example — Netflix

Netflix uses all three: REST for public-facing APIs consumed by external developers; gRPC for internal service-to-service calls (e.g., recommendation engine → streaming service), achieving ~10× throughput vs JSON/REST; GraphQL via their "Federated API" (GraphQL Federation) to let each device (TV, mobile, web) request exactly the fields needed for its UI, eliminating over-fetching that previously bloated mobile data usage by 30%.

4

Event-Driven Architecture

Async communication via events — Kafka as the backbone

🚗 Real-World Example — Uber

When a rider books a trip, Uber's Trip Service publishes a TripRequested event to Kafka. Six downstream services consume it independently: the Driver Matching service (finds nearby drivers), the Surge Pricing service (recalculates fares), the Maps service (pre-loads route data), the Notifications service (alerts the driver), the ETA service (estimates arrival), and the Analytics service (updates demand heatmaps). None of them call each other — they're all consumers of the same Kafka topic, allowing each team to deploy independently.

CQRS Pattern

Separate write and read models for independent optimization

🏦 Real-World Example — Banking (Axon Framework)

A bank's Account service uses CQRS: writes go through a normalized PostgreSQL schema (strict ACID, domain validation — e.g., reject overdrafts). Reads — like "show my last 100 transactions with merchant name and category" — are served from an Elasticsearch read model, pre-projected from domain events. The read model is eventually consistent (typical lag <100ms) but handles 50,000 QPS without touching the write DB. If the read model corrupts, replay all events to rebuild it from scratch — this is Event Sourcing + CQRS together.

6

Saga Pattern

Distributed transactions without 2PC — choreography vs orchestration

✈️ Real-World Example — Airbnb Booking

Airbnb's booking flow is an Orchestration Saga: the BookingOrchestrator coordinates four services — Calendar (block dates), Payment (charge guest), Messaging (notify host), and Payout (schedule host payment). If any step fails, it triggers compensating transactions in reverse: cancel payout → cancel message → refund payment → unblock dates. Airbnb chose orchestration over choreography because the booking flow has a clear sequence and requires auditability of which step failed and why.

Resilience Patterns

Circuit Breaker, Retry, Bulkhead, Rate Limiter — preventing cascading failures

🎥 Real-World Example — Netflix Hystrix → Resilience4j

Netflix coined the Circuit Breaker pattern in production — their Hystrix library (now deprecated) protected against cascading failures when the Recommendations service degraded. When Recommendations was OPEN (failing), the fallback returned a generic "Top 10 movies" list instead of a blank screen. Netflix also uses Bulkheads to isolate the streaming thread pool from the metadata thread pool, so a slow subtitle service never starves video delivery. Today most teams use Resilience4j with the same patterns.

API Versioning Strategies

Evolving APIs without breaking consumers

💳 Real-World Example — Stripe API

Stripe is the gold standard for API versioning. They use date-based URI versions (e.g., /v1/charges with a Stripe-Version: 2024-04-10 header). Each customer's API key is "pinned" to the version at sign-up time, so they never see breaking changes. When Stripe releases v2 of an endpoint, the old version continues working indefinitely for pinned customers. Their Pact-style contract tests verify every version still works on every deploy. This design has kept their API backwards-compatible for 10+ years.

Microservices Testing Strategies

Test pyramid — unit → integration → contract → E2E

🛒 Real-World Example — Shopify

Shopify's checkout service has 4 layers: 10,000+ unit tests running in 30 seconds; 2,000 integration tests using Testcontainers (MySQL, Redis, Kafka) running in 8 minutes; 200 Pact contract tests verifying their Payments API against every consumer (iOS app, Android app, web); and 15 E2E Playwright tests covering the critical "browse → cart → pay → confirm" journey against a staging environment. This pyramid keeps their 70-service monorepo deployment cycle under 20 minutes.

Anti-patterns & Migration

What goes wrong — and how to fix it with Strangler Fig

📦 Real-World Example — eBay & Zalando

eBay's original monolith ("V1") had a shared Oracle database accessed by all modules — a classic distributed monolith after they tried to split it. Their fix was the Strangler Fig: an API Gateway was placed in front, and over 3 years, new microservices (Search, Recommendations, Payments) were extracted one at a time, each with its own DB. Traffic was migrated route by route. Zalando (European e-commerce) similarly used dual-write migration when extracting their Catalog service — writing to both PostgreSQL (old) and MongoDB (new) for 6 months, comparing read results in shadow mode before cutting over.

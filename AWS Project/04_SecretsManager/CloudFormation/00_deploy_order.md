# ShopFlow Secrets Manager — Module 4: Deployment Guide

## What Is Secrets Manager?

AWS Secrets Manager stores sensitive values — database passwords, API keys, JWT signing keys — encrypted at rest using AWS KMS. Your application retrieves them at runtime using its IAM role. **The secret value never appears in code, config files, or environment variables as plain text.**

**The key difference from SSM Parameter Store (Module 5):**
- **Secrets Manager**: passwords and tokens that must be rotated. Costs $0.40/secret/month.
- **SSM Parameter Store**: non-sensitive config like endpoints and feature flags. Free.

---

## Secrets Created

| Secret | Path | What It Stores |
|--------|------|----------------|
| DB Master | `/shopflow/db/master` | RDS MySQL admin username + auto-generated password |
| DB App User | `/shopflow/db/app` | Spring Boot app DB username + auto-generated password |
| JWT Secret | `/shopflow/app/jwt-secret` | 64-char HS512 signing key for JWT tokens |
| Redis Auth | `/shopflow/app/redis-auth` | 32-char ElastiCache AUTH token |
| Third-Party | `/shopflow/app/third-party` | Stripe + SendGrid API keys (placeholder — update manually) |

## How Secrets Manager Works

```
Application startup:
  ┌──────────────┐         ┌─────────────────────┐       ┌──────────────────┐
  │  ECS Task    │ ──IAM→  │  Secrets Manager API │ ──→   │  Secret Value    │
  │  (ShopVerse) │         │  GetSecretValue       │       │  {"password":"X"}│
  └──────────────┘         └─────────────────────┘       └──────────────────┘
         │
         │  Injected as env var by ECS:
         │  DB_PASS = X (from the secret JSON)
         ↓
  Spring Boot reads: @Value("${DB_PASS}")
```

The ECS task definition references the secret ARN. ECS calls Secrets Manager at task start, extracts the value, and injects it as an environment variable. The task container never calls Secrets Manager directly.

## Deployment Steps

### Prerequisites

- Stack `shopflow-iam-policies` deployed (IAM roles need `secretsmanager:GetSecretValue` permission)
- No VPC or network dependency — Secrets Manager is a global service

### Step 1: Deploy the Stack

1. Open **AWS Console → CloudFormation → Create stack → With new resources**
2. Upload: `01_secrets.yaml`
3. Stack name: `shopflow-secrets`
4. Parameters:
   - **ProjectName**: `shopflow`
   - **Environment**: `dev`
5. **Check the IAM capabilities box** — this stack does NOT create IAM resources, but CloudFormation may show the warning anyway; it's safe to acknowledge
6. Click **Submit** → wait for `CREATE_COMPLETE` (~30 seconds)

### Step 2: Update the Third-Party Secret (Required)

The `third-party` secret is created with placeholder values. Update it with real API keys:

```bash
# Update the Stripe and SendGrid keys (replace with your actual keys)
aws secretsmanager put-secret-value \
  --secret-id /shopflow/app/third-party \
  --secret-string '{
    "stripe_secret_key": "sk_test_YOUR_ACTUAL_STRIPE_KEY",
    "stripe_webhook_secret": "whsec_YOUR_ACTUAL_WEBHOOK_SECRET",
    "sendgrid_api_key": "SG.YOUR_ACTUAL_SENDGRID_KEY"
  }'
```

Or do it in the console: **Secrets Manager → /shopflow/app/third-party → Retrieve secret value → Edit**.

## Verify After Deployment

1. Go to **AWS Console → Secrets Manager**
2. You should see 5 secrets with the `/shopflow/` prefix
3. Click `/shopflow/db/master` → **Retrieve secret value**
   - You should see: `{"username": "shopflow_admin", "password": "<32-char random string>"}`
   - Note: the password was auto-generated by Secrets Manager — you never chose it
4. Click `/shopflow/app/jwt-secret` → **Retrieve secret value**
   - You should see: `{"jwt_secret": "<64-char alphanumeric string>"}`

## How Auto-Generated Passwords Work

In `01_secrets.yaml`, the `DBMasterSecret` uses `GenerateSecretString`:

```yaml
GenerateSecretString:
  SecretStringTemplate: '{"username": "shopflow_admin"}'
  GenerateStringKey: "password"
  PasswordLength: 32
  ExcludeCharacters: '"@/\\'
```

This means:
- Secrets Manager starts with `{"username": "shopflow_admin"}`
- It generates a 32-character random password (excluding `"@/\` which break MySQL connection strings)
- It inserts the password at the `"password"` key
- Result: `{"username": "shopflow_admin", "password": "Xk9mPq2..."}`

**You never see the password during creation. It's generated, encrypted, and stored atomically.**

## How ECS Uses These Secrets

When we build the ECS module (Module 11), the task definition will look like this:

```json
"secrets": [
  {
    "name": "DB_PASS",
    "valueFrom": "arn:aws:secretsmanager:ap-south-1:123456789:secret:/shopflow/db/app:password::"
  },
  {
    "name": "JWT_SECRET",
    "valueFrom": "arn:aws:secretsmanager:ap-south-1:123456789:secret:/shopflow/app/jwt-secret:jwt_secret::"
  }
]
```

The format is: `<secret-arn>:<json-key>::`

ECS calls `GetSecretValue`, parses the JSON, extracts the named key, and injects it as the named environment variable. Spring Boot reads it the same as any env var.

## Rotation (Important Concept)

Secrets Manager can **automatically rotate** the DB password:
1. Lambda function generates a new password
2. Lambda updates the MySQL user's password in RDS
3. Lambda updates the secret value in Secrets Manager

**Your running Spring Boot app keeps working** because:
- It fetches the secret on each new DB connection (or connection pool reconnect)
- The transition period has both old and new passwords valid

We will wire up rotation when building the RDS module (Module 6).

**Warning for JWT secret**: rotating the JWT signing key **immediately invalidates all existing tokens** — every logged-in user is signed out. Coordinate with users before rotating.

## Fetching a Secret via AWS CLI (Manual Test)

```bash
# Get the full secret (JSON string)
aws secretsmanager get-secret-value \
  --secret-id /shopflow/db/master \
  --query SecretString \
  --output text

# Parse just the password using jq
aws secretsmanager get-secret-value \
  --secret-id /shopflow/db/master \
  --query SecretString \
  --output text | jq -r '.password'
```
